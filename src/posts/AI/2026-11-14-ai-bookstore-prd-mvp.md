# AI 서점 개발기 01: 아이디어를 MVP로 좁히기

AI 서점을 만들어보겠다고 마음먹었다. 이름만 보면 AI가 책을 골라주고, 취향을 분석하고, 대화까지 해주는 서비스가 떠오른다. 나 역시 처음에는 여러 온라인 서점과 콘텐츠 플랫폼을 연결하고 AI 추천과 독서 도우미까지 한 번에 만들고 싶었다.

그런데 만들고 싶은 기능을 적다 보니 범위가 계속 커졌다. 웹툰, 웹소설, 전자책, 종이책을 모두 다루고, 네이버와 카카오, 리디, 교보문고, YES24, 알라딘까지 연동하고, 개인 서재와 독서 기록에 AI 추천과 RAG까지 붙이는 식이었다.

이대로 시작하면 첫 화면을 만들기도 전에 설계만 하다 끝날 것 같았다. 그래서 코드를 작성하기 전에 먼저 해결하려는 문제와 첫 번째로 동작해야 할 사용자 흐름을 정리하기로 했다.

## 내가 해결하고 싶은 문제

콘텐츠를 소비하는 플랫폼은 여러 곳으로 나뉘어 있다. 웹툰은 한 앱에서 보고, 웹소설은 다른 앱에서 읽고, 전자책은 또 다른 서점에서 구매한다. 읽고 싶은 작품이나 이미 읽은 작품도 각 플랫폼에 흩어져 있다.

플랫폼마다 제공하는 기능은 충분하지만, 내가 어떤 작품을 가지고 있는지, 어디까지 읽었는지, 어떤 작품을 재미있게 봤는지를 한곳에서 돌아보기는 어렵다.

내가 만들고 싶은 건 새로운 콘텐츠 판매 플랫폼이라기보다 **내가 소비하는 콘텐츠를 모으고 기록하는 개인 서재**에 가깝다. 작품을 발견하고, 서재에 담고, 읽은 경험을 기록하면 그 기록이 쌓여 나만의 취향 데이터가 되는 구조다.

## 처음부터 AI를 앞세우지 않기로 했다

AI를 활용하는 프로젝트이지만, 첫 번째 기능부터 AI일 필요는 없다고 판단했다.

사용자가 작품을 검색하고 서재에 등록하고 독서 상태와 감상을 기록하는 기본 흐름이 없다면 AI가 분석할 데이터도 없다. 추천 모델을 먼저 붙이는 것보다 기록이 자연스럽게 쌓이는 제품을 만드는 일이 우선이다.

그래서 제품을 세 영역으로 나눴다.

| 영역 | 역할 | 핵심 경험 |
| --- | --- | --- |
| Online Bookstore | 작품 탐색 | 여러 유형의 작품을 검색하고 제공 플랫폼을 확인한다 |
| My Library | 개인 서재 | 작품을 모으고 독서 상태와 감상을 기록한다 |
| AI Reading Assistant | 취향 이해와 추천 | 쌓인 기록을 바탕으로 작품을 추천하고 질문에 답한다 |

이렇게 나누니 AI는 서비스 전체를 대신하는 기능이 아니라, 사용자가 쌓아둔 데이터를 더 잘 활용하게 해주는 역할이라는 점이 분명해졌다.

## MVP에서 할 일과 하지 않을 일

PRD를 작성하면서 가장 신경 쓴 부분은 기능을 추가하는 것보다 초기 범위를 제한하는 일이었다.

첫 번째 MVP에서 반드시 필요한 기능은 다음과 같이 정리했다.

- 이메일 기반 회원가입과 로그인
- 작품 목록, 제목·작가 검색, 작품 상세 정보
- 작품 직접 등록과 외부 플랫폼 링크
- 개인 서재 등록 및 조회
- 관심, 읽는 중, 완독, 중단, 보류 상태 관리
- 페이지·회차·퍼센트 단위의 진행률 기록
- 별점과 감상평 작성

반대로 플랫폼 구매 내역이나 독서 진행률을 자동으로 가져오는 기능, 자체 결제, 커뮤니티, 모든 플랫폼의 실시간 연동은 초기 범위에서 제외했다.

특히 외부 플랫폼 연동은 기술적으로 가능해 보인다는 이유만으로 진행하지 않기로 했다. 공식 API 또는 이용이 허용된 데이터만 사용하고, 연동할 수 없는 플랫폼은 수동 작품 등록과 외부 링크로 대응한다. 작품 설명과 표지 이미지 역시 이용 조건과 저작권을 확인해야 한다.

처음부터 모든 플랫폼을 연결하는 것보다, 사용자가 작품을 직접 등록하더라도 서재와 독서 기록을 실제로 사용할 수 있는 상태를 먼저 만드는 편이 현실적이라고 봤다.

## 작품과 플랫폼을 별도 데이터로 다루기

초기 데이터 모델에서 중요하게 본 것은 작품과 제공 플랫폼을 분리하는 것이다.

하나의 작품이 여러 플랫폼에서 제공될 수 있다. 작품 자체의 정보와 플랫폼별 외부 ID, 상세 페이지 URL을 하나의 데이터로 묶어버리면 같은 작품이 플랫폼 수만큼 중복될 수 있다.

그래서 내부 작품 식별자와 플랫폼별 식별자를 분리하는 방향을 잡았다.

- `Content`: 제목, 작가, 콘텐츠 유형, 장르와 태그 등 작품 자체의 정보
- `ContentPlatform`: 제공 플랫폼, 외부 작품 ID, 외부 URL 등 플랫폼별 정보
- `UserLibrary`: 사용자가 작품을 서재에 담고 기록하는 정보
- `Review` / `ReadingNote`: 별점, 감상평, 개인 메모

아직 ERD를 확정한 것은 아니다. 현재는 PRD에서 필요한 데이터의 책임과 관계를 구분한 단계다. 실제 테이블 구조와 중복 작품 판별 기준은 IA와 ERD를 작성하면서 더 구체화해야 한다.

## AI 기능도 단계적으로 나누기

AI 기능은 처음부터 Agent나 RAG를 구현하는 대신, 데이터가 쌓이는 순서에 맞춰 확장하기로 했다.

1. **규칙 기반 추천**: 별점, 선호 장르, 완독 작품, 작가와 태그를 활용한다.
2. **자연어 검색**: 사용자의 문장을 콘텐츠 유형, 장르, 완결 여부 같은 검색 조건으로 변환한다.
3. **Embedding과 Vector Search**: 작품 메타데이터와 개인 감상평·메모의 의미적 유사도를 검색한다.
4. **RAG 독서 도우미**: 실제 독서 기록을 검색한 뒤 그 결과를 근거로 답변한다.

LLM이 작품 정보를 임의로 만들어내는 구조는 피하고 싶다. AI는 검색 조건을 구조화하거나 기록을 해석하는 역할을 맡고, 실제 작품 조회와 추천 대상 선정은 서비스가 가진 데이터에 기반해야 한다. 추천 이유도 사용자의 어떤 기록과 작품의 어떤 특성이 연결됐는지 설명할 수 있어야 한다.

## 기술 스택은 아직 확정하지 않았다

현재 PRD에는 Next.js와 TypeScript, Java 21과 Spring Boot 3, PostgreSQL과 pgvector, Python과 FastAPI를 기술 방향으로 적어두었다.

다만 이 목록은 확정된 구현 스택이 아니다. 프론트엔드와 백엔드 저장소를 분리할지, AI 모듈을 별도 서비스로 운영할지, 무료 인프라만으로 어디까지 배포할 수 있을지는 실제 구현 난이도와 운영 비용을 확인한 뒤 결정해야 한다.

이번 프로젝트에서는 기능을 많이 넣는 것만큼이나 지속적으로 운영할 수 있는 구조인지가 중요하다. 로컬에서 핵심 기능을 실행할 수 있어야 하고, 유료 API나 무료 플랜의 제약 때문에 AI 기능을 사용할 수 없더라도 기본 검색과 서재 기능은 동작해야 한다.

## 현재까지 정리한 것과 다음 작업

이번 단계에서 완료한 것은 제품 아이디어를 PRD 초안으로 정리한 일이다.

- 해결하려는 문제와 주요 사용자 정의
- Online Bookstore, My Library, AI Reading Assistant의 제품 영역 구분
- MVP Must 기능과 초기 제외 범위 정리
- 작품·플랫폼·사용자 서재 데이터의 기본 책임 구분
- AI 기능의 단계별 도입 방향 정리
- 기술 스택 후보와 비용·연동 관련 리스크 기록

아직 화면이나 API를 구현하지 않았고, 외부 플랫폼 연동 가능 여부도 검증하지 않았다. PRD 자체도 미결정 항목이 남아 있는 Draft 상태다.

다음에는 사용자 관점에서 화면과 메뉴 구조를 정리하는 IA를 만들고, 각 화면에서 어떤 행동을 할 수 있어야 하는지 구체화할 예정이다. 그 다음 ERD와 API 명세로 이어가려고 한다.

처음부터 거대한 AI 서비스를 만들려고 하기보다, 내가 실제로 사용하고 싶은 작은 서재부터 동작하게 만드는 것. 지금 단계에서 가장 중요한 방향은 그 정도로 정리됐다.
